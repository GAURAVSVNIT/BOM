The engine decision, from evidence

Published benchmarks put openpyxl at full fidelity (16/16) and python-calamine at 1/16 but 9× faster — calamine reads values and drops merged cells, formatting and comments. For 119 workbooks speed is irrelevant and fidelity is everything, so: openpyxl as the primary reader, calamine as an independent second opinion, plus raw zip parsing for the parts neither library exposes.

Every cell is read twice and reconciled. 99.85% agreement across 172,092 cells, and all 234 remaining disagreements are Excel error cells (#DIV/0!, #NAME?) that openpyxl surfaces and calamine reports as empty. Zero genuine value conflicts.

What merge-awareness actually recovers

Every cell now records whether its value is its own or an echo of a merged range. That distinction matters: on these sheets a label routinely spans two or three columns, so a naive "first non-empty cell to the right of the label" returns the label again.

EXPORT ENQUIRY.xlsx / BAG TYPE-1, header row 9

raw openpyxl   C1=BAG TYPE   C3=U+2 PANEL WITH CORNER LOOP   C7=DOC PKT   C8=NA
merge echoes   C2~BAG TYPE  C4~U+2 PANEL…  C5~U+2 PANEL…  C6~U+2 PANEL…  C9~NA  C10~NA

A right-scan that does not know C2 is an echo of the label returns "BAG TYPE"
as the bag type. The reader skips echoes of the label's own merge origin.

Two further gaps the first parser had, found by inspecting what it missed rather than assuming it was right:

  • TOP SPOUT was the single most common top label — 219 sheets — and was not in the label list at all. Coverage went 51% → 99.6%.
  • A second sheet layout exists (SR.NO. | COMPONENT | FABRIC SIZE CM | CUT SIZE | QTY | GSM) carrying an explicit QTY column. Grand-total detection went 90.2% → 99.8%.

Firewall — enforced structurally, not by discipline

build_order_spec() takes the header dict and the dimensions. It is never handed the component table. A test then asserts no BuildSpec-only field (body_gsm, belt_gpm, family, dust_proof…) appears in any OrderSpec or any adapter-A target. PASS.

The round trip is the whole point. Text is synthesised from OrderSpec_gold; an independent parser — sharing no code with the generator — re-reads the generated text and must recover the same values. Any mismatch is discarded, never repaired.

Field dropout follows the corpus rates so a synthetic enquiry is as incomplete as a real one: liner absent 78%, printing 43%, target weight 9%, SWL 5%. Corpus noise is injected verbatim — PANNEL, CLOUSER, gr/m2, 3", 05:01.

Each style is graded only on fields it can structurally express. A printed technical data sheet carries no LL/SL loop lengths, so grading it on those would have discarded sound rows — that single fix took the TDS style from 28 rows to 325.

One false alarm worth naming

The leakage check first reported 48 identical inputs across splits. It was comparing only the first 600 characters of the JSON, which is identical for every sparse OrderSpec. Hashing the whole input gives zero overlap. A validator that is wrong in the alarming direction is still wrong — it now hashes the full object.

06 Known limits — stated plainly

  1. Adapter A is trained on reconstructed enquiries. The corpus holds the engineer's transcription of the enquiry, not the enquiry itself. Every row is round-trip verified, but the distribution is synthetic. eval_real is the only honest measure — and it holds 13 documents. Keeping the next twenty raw enquiries is still the highest-value action available to this project.
  2. product_contents is empty on all 482 rows. Answer C1 says this field explains the 68% GSM spread, and no sheet records it. The schema is ready; the data is not. Until it exists, adapter B has to learn GSM from geometry and neighbours alone.
  3. req_weight_g appears on 7% of sheets, quoted_weight_g on 76%. Per G4 these are different facts and are kept apart. The solver falls back to the quoted figure.
  4. Five families have no geometry yet — present in the gold layers and in adapter B, but the renderer cannot score them, which is most of the 10.2% median error.
  5. Eight scanned enquiries have no text layer and are listed in eval_real/pending_ocr.json rather than silently dropped. OCR plus hand labelling would roughly double the real eval set.
