  Target weight is present in 92.7% of orders; SWL is missing in 8.6%. The
  finished BOM lands within 2% of the stated target in 68% of orders. The BOM is
  an inverse problem — solve for the configuration that hits the target weight,
  with the load chart as a hard floor. Your pipeline is single-pass and has
  nowhere to express that. This is the biggest win available and needs no GPU.

  Qwen's job: the BuildSpec, not the BOM

  One LoRA adapter emitting ~70 closed-vocabulary decision fields —
  classification, material selection, loop geometry, component switches,
  commercial keys — under grammar-constrained decoding. It may say body_gsm: 
  150; it may never say cut_cm: 263 or weight_g: 366.885. A deterministic
  renderer expands that into all six blocks. Then the solver loop feeds the
  weight gap back so the model adjusts the knobs it owns.

  That's ~90% of the judgement and 0% of the arithmetic.

  Direct generation: no. ~90 numeric cells per sheet, 58.3% of them
  non-integers. At 99% per-number accuracy the whole sheet is right 40% of the
  time; at 99.9%, 91%. A 4B model won't hit 99.9% on three-factor decimal
  multiplication. Keep a full-BOM adapter only as a labelled fallback for
  omega/tunnel/box/container/platen, which the rule engine doesn't model.

  Your data question has a good answer

  Every BOM sheet already contains its own enquiry. Before doing any
  engineering, the engineer transcribes what the customer asked into the header
  block — A3:C11 (customer, SWL, SF, qty, bag type, colour, required weight) and
  G3:L11 (printing, ext size, int size, loop, top, bottom, doc pocket, liner,
  packing). That header is the customer's request, already normalised by a
  human. All 395 sheets have one. The raw WhatsApp message is gone; its content
  is not.

  So one extraction pass over each sheet produces three aligned records:

  - OrderSpec_gold ← header block only — what the customer said
  - BuildSpec_gold ← header + component table + INSTRACTION + tape/loom blocks —
    what the engineer decided
  - PhysicalBOM_gold ← component table verbatim — used only to test the
    renderer, never as a training target

  The critical rule is a firewall: OrderSpec_gold must be built from the header
  alone. If one field leaks in from the component table, the extractor learns to
  predict engineering decisions from the enquiry, and the evaluation becomes
  meaningless while looking excellent. Enforce it in code — the builder function
  physically cannot see the rest of the sheet.

  Two adapters, and the split matters

  ┌──────────────────┬──────────────────────────┬──────────────────────────┐
  │                  │  Adapter A — extraction  │       Adapter B —        │
  │                  │                          │      configuration       │
  ├──────────────────┼──────────────────────────┼──────────────────────────┤
  │ On a missing     │ emit not_specified       │ fill it in from          │
  │ field            │                          │ experience               │
  ├──────────────────┼──────────────────────────┼──────────────────────────┤
  │ Worst failure    │ asserting what isn't     │ leaving a field null     │
  │                  │ there                    │                          │
  ├──────────────────┼──────────────────────────┼──────────────────────────┤
  │ Primary metric   │ hallucination rate < 2%  │ per-field accuracy       │
  ├──────────────────┼──────────────────────────┼──────────────────────────┤
  │ Training rows    │ ~1,600, mostly synthetic │ ~1,800, mostly real      │
  └──────────────────┴──────────────────────────┴──────────────────────────┘

  filling blanks is sometimes right and sometimes forbidden, with nothing in
